# 0001. RS256 access tokens with a JWKS endpoint instead of a shared HS256 secret

- **Status**: Accepted
- **Date**: 2026-11-17

## Context

Identity issues the access tokens that Orders (NestJS), Payments (.NET), Inventory (Java) and
Notifications (Python) verify. Each service must be able to check a token on its own, without
calling Identity per request (services do not call each other over HTTP).

With HS256 the same secret both signs and verifies. Every verifying service would hold a secret
that can also **mint** tokens, so a leak from any of four codebases, images or configurations
would let an attacker forge an `ADMIN` token. Rotating the secret would mean a coordinated
redeploy of every service at once.

## Decision

We will sign access tokens with **RS256** using `jose`:

- Identity alone holds the private key. It comes from the environment or a mounted file
  (`JWT_PRIVATE_KEY_PATH`) and is never committed; `keys/` and `*.pem` are git-ignored. A
  development key pair is generated by a documented script.
- `GET /.well-known/jwks.json` publishes the public keys, each with its `kid`. The JWT header
  carries the `kid` of the signing key.
- The JWKS can hold **more than one active key**, so a new key can be introduced, used for
  signing, and the old key removed only after the tokens it signed have expired.
- Tokens are short-lived (15 minutes by default, `JWT_ACCESS_TTL_SECONDS`) and carry `sub`,
  `customerId` (customers only), `roles`, `iss`, `aud`, `iat`, `exp` and `jti`.
- Verifying services fetch and cache the JWKS, and check the signature, `iss`, `aud` and `exp`.
  They take `customerId` from the verified token, never from the request.

## Consequences

- A verifying service can never forge a token; a leaked public key is harmless.
- Key rotation is a change in Identity only: verifiers pick up new keys from the JWKS by `kid`.
- Every stack has a mature JWKS/RS256 library, so the polyglot services need no shared code.
- RS256 signatures are larger and slower than HS256; at our token lifetimes this is negligible.
- Revocation of an access token is not possible before it expires; short lifetimes bound the
  exposure, and role or status changes take effect at the next login or refresh.
- Follow-up: the token story adds the key generation script, the JWKS endpoint and the signer.
