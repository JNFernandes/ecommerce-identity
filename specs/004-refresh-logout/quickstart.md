# Quickstart: Refresh the session and log out (US-04)

## Prerequisites

- Local infrastructure is running. In `ecommerce-infra`, run `docker compose up -d` (Postgres on `localhost:5435`).
- A `.env` file copied from `.env.example`, with a key generated by `npm run keys:generate`.
- Run `npm run migration:run` (this story adds no migration) and then `npm run start:dev`.
- A registered customer, created with `POST /auth/register` (see US-01's quickstart).

## Scenarios

```bash
# 1. Log in and keep the refresh token
LOGIN=$(curl -s -X POST localhost:3001/auth/login -H 'content-type: application/json' \
  -d '{"email":"ana@example.com","password":"correct-horse-battery"}')
RT1=$(echo "$LOGIN" | jq -r .refreshToken)

# 2. Refresh → 200, login shape, new refreshToken (RT2)
RT2=$(curl -s -X POST localhost:3001/auth/refresh -H 'content-type: application/json' \
  -d "{\"refreshToken\":\"$RT1\"}" | tee /dev/stderr | jq -r .refreshToken)

# 3. Reuse RT1 → 401 {"message":"invalid refresh token"}; then RT2 also → 401 (family revoked)
curl -i -X POST localhost:3001/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$RT1\"}"
curl -i -X POST localhost:3001/auth/refresh -H 'content-type: application/json' -d "{\"refreshToken\":\"$RT2\"}"

# 4. Log out (fresh login) → 204; refresh with that token → 401; logout with garbage → 204
curl -i -X POST localhost:3001/auth/logout -H 'content-type: application/json' -d '{"refreshToken":"unknown"}'

# 5. Unknown property → 400
curl -i -X POST localhost:3001/auth/refresh -H 'content-type: application/json' -d '{"refreshToken":"x","extra":1}'
```

Expected results:

- Step 2: the new access token verifies against `GET /.well-known/jwks.json` and has a new `jti`.
- Step 3: both 401 bodies are identical.
- Storage check (`psql`): every row of the family has `revokedAt` set, and RT1's `replacedBy` is RT2's id.
- Session limit: restart with `JWT_SESSION_MAX_SECONDS=60` and `JWT_REFRESH_TTL_SECONDS=60`. Log in, refresh, and check that the new token's `expiresAt` is no later than login time + 60 s. After 60 s, refresh returns 401.
- Rate limit: the 31st refresh from one IP within a minute returns 429.

## Automated checks

```bash
npm run test:unit
npm run test:integration   # needs Docker (testcontainers)
npm run test:component     # needs Docker
```

The component tests cover:

- the old token no longer working after a refresh;
- reuse revoking the whole family;
- two parallel refreshes giving exactly one 200;
- logout followed by refresh returning 401;
- logout with an unknown token returning 204;
- the session limit;
- 429 past the rate limit;
- no token in the captured logs;
- refresh and logout working while Kafka is unreachable.

## Result (2026-11-18, run by hand against `node dist/main.js`, local ecommerce-infra Postgres, Kafka not running)

- **Steps 1–2**: refresh → 200 with exactly the four login fields; new access token verifies through `GET /.well-known/jwks.json`, new `jti`. ✅
- **Step 3**: reuse RT1 → 401, then RT2 → 401; bodies identical `{"message":"invalid refresh token","error":"Unauthorized","statusCode":401}`. Storage: every family row has `revokedAt`, RT1's `replacedBy` = RT2's id. ✅
- **Step 4**: logout (fresh login) → 204 empty body; refresh with that token → 401; logout `unknown` → 204. ✅
- **Step 5**: unknown property → 400. ✅
- **Session limit** (`JWT_SESSION_MAX_SECONDS=60`, `JWT_REFRESH_TTL_SECONDS=60`): new token `expiresAt` = login + 60 s; refresh after 62 s → 401. `JWT_SESSION_MAX_SECONDS=59` with TTL 60 → startup exit 1 with `JWT_SESSION_MAX_SECONDS must be >= JWT_REFRESH_TTL_SECONDS`. ✅
- **Rate limit**: the 31st refresh within a minute → 429. ✅
- **Logs**: `refresh succeeded`, `refresh token reuse detected`, `refresh refused: reason=REUSED` with ids and IP only; no token or hash in the log. Kafka was down throughout; refresh and logout were unaffected. ✅
